# Tests — Le Musée des 100

Trois niveaux : unitaires (Vitest), E2E smartphone (Playwright), vérifications CI (lint, types, build, budgets). Cette page explique la stratégie et comment lancer chaque niveau. Propriétaire : agent QA — `e2e/**` et ce fichier.

## 1. Unitaires (Vitest, jsdom)

```
pnpm test          # une passe
pnpm test:watch    # mode watch
```

jsdom n'a pas de WebGL (`HTMLCanvasElement.getContext()` n'est pas implémenté) : les tests unitaires couvrent la logique pure (physique de déplacement, plan du musée, tampons, i18n…) et les composants React qui vivent dans le DOM (HUD, fiches, dialogue, personnalisation…), jamais un `<Canvas>` monté. Le rendu 3D lui-même n'est vérifié qu'en E2E (ci-dessous), à l'œil via les captures d'échec, et indirectement par les tests DOM qui pilotent le state que la scène 3D consomme.

1818 tests, 101 fichiers au 01/10/2026 (V5, chat avec Rémi · IA : `src/features/remiChat/` apporte `useRemiChat`, `RemiChat`, `useChatViewport` et ses textes ; 525/41 à la deuxième passe, 318/26 à la première), un fichier `*.test.ts(x)` par module à côté du code qu'il couvre. Sous forte charge de la machine (load average ~25), quelques tests sensibles au temps d'autres modules (présence temps réel) ont échoué une fois sur une première passe complète puis réussi sur la suivante ; ceux du chat ont été rejoués 6 fois sous cette charge sans un échec.

## 2. E2E smartphone (Playwright)

```
pnpm e2e
# ou, en local sans navigateur Playwright téléchargé (voir docs/ARCHITECTURE.md) :
PW_CHROMIUM_PATH="$HOME/.agent-browser/browsers/chrome-149.0.7827.54/Google Chrome for Testing.app/Contents/MacOS/Google Chrome for Testing" pnpm e2e
```

`playwright.config.ts` (non modifiable depuis ce module) construit puis sert l'app (`pnpm build && pnpm preview`, port 4173) et lance chaque test sur trois projets : `iphone` (iPhone 13), `android` (Pixel 7), `desktop`. WebGL tourne en logiciel (SwiftShader, `--use-gl=angle --use-angle=swiftshader`) : plus lent qu'un vrai GPU, mais suffisant pour vérifier que la scène se construit et réagit.

### Poignée de test `window.__musee`

Activée par `?e2e=1` (ou en dev), exposée par `src/scene/debugApi.ts` (contrat de l'agent intégration, non modifiable ici) :
- `state()` → l'état zustand complet (écran, langue, avatar, tampons, actions comme `openPerson`/`closeDialogue`…), y compris désormais `layout` (plan du musée) et `mapOpen`.
- `player` / `input` → position/vitesse du joueur et entrée de déplacement courants (objets mutables, hors React).
- `teleport(x, z, rotY?)` et `goToPerson(personId)` → placent le joueur, y compris face à un portrait donné.
- `renderInfo()` (deuxième passe) → compteurs du renderer three.js (`calls`, `triangles`, `geometries`, `textures`), branché par `src/scene/DebugProbe.tsx` une fois le `<Canvas>` monté. Absent brièvement au tout premier rendu : les tests qui en ont besoin l'attendent (`waitForRenderInfo`, ci-dessous).
- `cameraPosition()` (nouveau, vérification finale de la deuxième passe) → position courante de la caméra (dernière image), branchée par `src/scene/DebugProbe.tsx` comme `renderInfo()`. Sert uniquement à `waitForCameraSettled` (ci-dessous) : ne pas l'utiliser pour dériver une position monde attendue (dupliquerait la géométrie de caméra du module joueur, contrat `cameraRig`/`cameraPositionFor`).

`e2e/support/museeApi.ts` enveloppe cette poignée (types locaux volontairement dupliqués et minimaux : le projet TypeScript des tests, `tsconfig.node.json`, n'a pas la lib DOM que le code applicatif utilise — voir le commentaire en tête de ce fichier) et fournit les parcours communs : `gotoMusee` (qui intercepte aussi `/api/remi`, voir « Chat avec Rémi · IA » ci-dessous), `enterMuseum` (titre → jeu), `dismissWelcomeDialogue` (ferme la bulle d'accueil de Rémi — bouton « Passer » — et tout dialogue scripté encore affiché ; si un test avait ouvert le chat avec Rémi · IA, le ferme d'abord par son bouton ; une quarantaine d'appels en dépendent), `openRemiChat` (ouvre le chat comme l'action « Parler à Rémi », sans marcher jusqu'au comptoir), `teleport`/`goToPerson`, `museeState`/`museePlayer`/`museeInput`, `openPersonViaState`/`closePersonViaState` (ouvre/ferme une fiche sans naviguer en 3D, pour les tests de tampons et du plan), `collectConsoleIssues`, `hasHorizontalOverflow`, `museeRenderInfo`/`waitForRenderInfo` (compteurs de rendu), `roomCenter` (centre d'une salle du plan, pour se téléporter « au milieu d'une aile »), et depuis la vérification finale de la deuxième passe `waitForCameraSettled` (voir « Découvertes » ci-dessous). `e2e/support/supabaseEnv.ts` lit `.env.local` directement (jamais committé) pour un test de joignabilité réseau Supabase avant le test `@live` de présence — jamais une vraie connexion Realtime.

### Locale du navigateur

Sans langue déjà choisie, l'app retombe sur `navigator.language` (`initialLang`, `src/state/gameStore.ts`). Le Chromium de test démarre en anglais par défaut (`en-US`) si rien ne le précise : les specs qui vérifient un texte français explicite fixent donc `test.use({ locale: 'fr-FR' })` en tête de fichier (`title-lang`, `customize`, `dialogue`, `portraits`, `persistence`, `stamps`, `museum-map`, `portrait-placeholder`, et le test de sous-titre de `loading`). Les autres (mouvement, paysage, performance, accessibilité, chargement/console, son, aide au premier pas, mode regard, présence) sont indifférents à la langue et ne fixent rien.

### Chat avec Rémi · IA (V5, WEL-920)

Le chat (`src/features/remiChat/`) poste sur `/api/remi` et lit un flux `text/event-stream` (contrat : `src/features/remiChat/contract.ts`). **Aucun test E2E n'appelle le vrai réseau** : `gotoMusee` pose `stubRemiDefault` (`e2e/support/remiApi.ts`) sur le contexte, une réponse courte valable pour tous les tests ; un test qui veut piloter la réponse appelle `stubRemiApi(page, …)` (les routes d'une page sont prioritaires sur celles du contexte, comme pour Supabase) : flux normal (`reply`), flux terminé par un événement `error` (`sse-error`), erreur HTTP avant tout flux (`http`, 503/429/400), ou requête jamais servie (`hang`, pour vérifier l'annulation). Les corps sont au format EXACT du contrat (`data: <json>` par événement, terminé par `done` ou `error`), donc valables avec le vrai client.

Les tests de `remi-chat.spec.ts` préfixés « client : » exigent le vrai `client.ts` (qui fait le `fetch`). Le bouchon posé par l'orchestrateur répond « Bonjour, je suis Rémi. » sans réseau : avec lui, ces cinq tests échouent sur l'assertion de la requête reçue ou du texte du flux, ce qui est attendu tant que l'agent `chat-api` n'a pas livré. Les autres ne dépendent pas du client.

Le chat ne s'ouvre qu'au comptoir (« Parler à Rémi », `interact()` → `openRemiChat()`) : à la première entrée, l'accueil de Rémi est la bulle `dialogue-box` en bas de l'écran (`App.tsx`, comme avant la V5), et `dismissWelcomeDialogue` la ferme. Les specs qui ont besoin du chat l'ouvrent avec `openRemiChat` (même appel que l'action) ; `remi-chat.spec.ts` teste en plus le vrai geste (téléportation au comptoir, bouton d'action) et, explicitement, qu'il ne s'ouvre PAS à l'entrée.

Le chat est translucide : le musée reste visible derrière Rémi et derrière les bulles, figé (`frameloop="never"`, `src/scene/Experience.tsx`). Un test qui lit la position de la caméra ou attend `waitForCameraSettled` doit le faire chat fermé. Redimensionner un `<canvas>` en efface le contenu et `invalidate()` est sans effet en `never` : `PausedRepaint` (même fichier) redessine l'image une fois, dans la même tâche, dès que R3F change la taille ou le ratio de pixels. Le test « musée figé derrière le chat » le prouve en photographiant l'élément `game-canvas` (chat masqué par une feuille de style, état inchangé) après chaque redimensionnement, une fois le tampon de dessin changé de taille ; sans `PausedRepaint`, les captures sont uniformes (le fond du body) et le test échoue. Même garantie si le contexte WebGL du musée est perdu pendant le chat (téléphone saturé par deux scènes) : `useCanvasRecovery` remonte un `<canvas>`, et `PausedRepaint`, monté dans le `Suspense`, dessine alors une image complète (`advance`) dès que la scène est prête ; le test provoque la perte (`WEBGL_lose_context`) et vérifie que le nouveau canvas n'est ni noir ni uniforme (il échoue sans cet effet : vérifié en le retirant).

Test « le musée est visible derrière… » : `sceneMatch` découpe la capture avec chat et la capture du musée seul en blocs de 24 px et compte, parmi les blocs où le musée seul a du relief (écart-type de luma ≥ 6), ceux où la corrélation de luma entre les deux captures dépasse 0,85 ; le voile et le flou changent les valeurs, pas le relief, alors qu'un aplat ou un dégradé opaque fait tomber la corrélation à zéro. Les blocs cachés par Rémi, les bulles ou le panneau flouté ne passent pas non plus, d'où un seuil sur la PART (0,2), pas sur la totalité. Test « contraste » : le chat est photographié texte masqué (`color: transparent`), et `minTextContrast` calcule, pixel par pixel sous la zone de chaque texte, le contraste entre la couleur réelle du texte (alpha compris) et le fond ; le 1er centile doit rester ≥ 4,5:1 (titre, mention IA, bulles de Rémi et du visiteur, suggestion, texte indicatif du champ).

Statut à jour après la vérification finale de la première passe (issue WEL-863, 2026-09-25) : `pnpm verify` est vert et la suite E2E complète est passée (voir historique de l'issue). Les deux bugs applicatifs d'origine sont corrigés et leurs tests ne sont plus `test.fixme` :

1. ~~`/favicon.ico` manquant (404 en console)~~ — **corrigé** : `public/favicon.ico` ajouté (module intégration). `loading.spec.ts` › *pas d'erreur console au chargement* passe désormais sur ce point.
2. ~~Contraste insuffisant du pied de l'écran titre~~ — **corrigé** : `.ui-title__footer` utilise `--ink` (7.3:1) au lieu de `--ink-soft` (3.69:1) dans `src/ui/ui.css` (module ui). `accessibility.spec.ts` › *écran titre* passe désormais sur ce point.

Une violation de contraste observée une seule fois en cours de mise au point (badge d'aile `.ui-portrait__wing`, ratio 2.52:1) ne s'est jamais reproduite (6/6 vert avant et après un durcissement préventif du module ui sur l'animation d'ouverture de la fiche) : non actée comme bug confirmé, à surveiller si elle réapparaît.

**Flake identifié et corrigé côté test lors de cette vérification finale** — `accessibility.spec.ts` › *écran titre*, une seule reproduction (projet android) sur l'ensemble des repasses de cette session : tous les textes du panneau titre (`.ui-title__eyebrow`, `h1`, `.ui-title__subtitle`, `.ui-title__enter`, `.ui-title__banner`) rapportés en contraste très insuffisant (~1.1–1.2:1) d'un coup. Cause : `.ui-title__panel` apparaît via l'animation d'opacité `ui-title-in` (700 ms, `src/ui/ui.css`) ; `toBeVisible()` de Playwright ne considère que la taille et `display`/`visibility`, pas l'opacité, donc le test peut lancer `AxeBuilder` en plein fondu — texte et fond encore semi-transparents sur le ciel 3D derrière, couleurs quasi identiques. Corrigé en ajoutant `test.use({ reducedMotion: 'reduce' })` en tête du fichier : déclenche `@media (prefers-reduced-motion: reduce)` (`src/styles/global.css`), qui coupe la durée des animations à 0.01 ms — le mécanisme d'accessibilité que `docs/DESIGN.md` prévoit déjà pour ce genre de cas. N'a pas nécessité de modification du module ui (aucune animation retouchée) ; documenté ici plutôt que dans `test.fixme` car corrigé et vert de façon reproductible dans les passages suivants.

**Bug corrigé depuis (deuxième passe)** — ~~`loading.spec.ts` › *pas d'erreur console au chargement*, `test.fixme`~~ : **`test.fixme` retiré**. La migration `supabase/migrations/20260924120000_people.sql` a été appliquée au projet distant (module **supabase**, WEL-854) — vérifié ici par un appel REST anonyme direct à `/rest/v1/people?select=*&published=eq.true` : `200` et `[]` (table vide, en attendant l'import de la vraie liste), là où on avait `PGRST205` (404) avant la migration. ### Découvertes de cette deuxième passe (tests, pas de bug applicatif)

**Flake pré-existant, root-causé et corrigé lors de la vérification finale de la deuxième passe** — `movement.spec.ts` › *tap au sol déclenche un déplacement automatique*, échouait parfois (`player.moving` ne passe jamais à `true`) sous forte charge parallèle. Le passage précédent (voir historique de ce fichier) l'avait attribué à de la pure contention CPU (thread principal saturé) après avoir constaté qu'augmenter le budget du `expect.poll` (2 s → 5 s) ne le corrigeait pas — ce diagnostic était incomplet : augmenter un budget d'attente APRÈS le tap ne pouvait de toute façon rien changer, parce que la cause n'est pas une transition trop lente.
Cause réelle, confirmée par instrumentation directe (position de caméra échantillonnée pendant le test à l'aide d'un script Playwright ad hoc, non conservé — voir le commentaire de `waitForCameraSettled`, `e2e/support/museeApi.ts`, pour le mécanisme) : `beforeEach` téléporte le joueur (`teleport`, saut instantané) juste avant le tap, mais la caméra le suit avec un **amortissement exponentiel** (`Player.tsx`, `CAMERA_DAMP_RATE = 6`) — elle reste un instant « en transit » entre l'ancienne position (celle du spawn) et la nouvelle. Le tap au sol convertit un point écran en point au sol par un rayon lancé depuis la caméra *courante* (`screenToFloor`) : lancé pendant que la caméra est encore en transit, ce rayon peut viser un point bien plus proche du joueur que la cible en régime établi — parfois sous `TAP_STOP_DISTANCE` (0,3 m, `Player.tsx`), auquel cas le tap est immédiatement traité comme « déjà arrivé » et `moving` ne passe jamais à `true`, quelle que soit la durée d'attente ensuite. Sous forte charge parallèle, moins d'images s'écoulent réellement entre le `teleport()` et le tap (le test, lui, s'exécute à la même vitesse en temps réel) : la caméra a donc convergé moins loin, ce qui rapproche mécaniquement la cible du seuil et rend l'échec bien plus fréquent — d'où le lien, réel mais mal interprété au passage précédent, avec la charge parallèle.
**Corrigé côté test** (pas un bug de gameplay réel : `teleport()` est un raccourci de test, un joueur réel ne subit jamais un tel saut instantané — voir `docs/ARCHITECTURE.md`) en exposant `cameraPosition()` (`src/scene/debugApi.ts` + `src/scene/DebugProbe.tsx`, module intégration) et en ajoutant `waitForCameraSettled` (`e2e/support/museeApi.ts`), qui attend que la position de la caméra ne bouge plus avant de taper — appelé dans le `beforeEach` de `movement.spec.ts`, juste après `teleport`. Vérifié : sous la charge qui faisait échouer 19 exécutions sur 20 avant ce correctif (`--repeat-each=20 --workers=4`, 4 cœurs virtuels partagés entre plusieurs scènes SwiftShader), il n'en restait que 2 sur 40 après. Ce résidu est expliqué juste en dessous (2ᵉ cause, CI du 30/09) : ce n'était pas une perte de contexte WebGL.

**2ᵉ cause du même symptôme, vue en CI le 30/09 et corrigée** — `movement.spec.ts` › *tap au sol* échouait sur `android` (deux fois sur deux, retry compris : runs 36732896400 et 36741633810) et sur `iphone` (« flaky », réussi au retry), jamais sur `desktop`. L'échec n'était pas dans le tap mais dans le `beforeEach` : `waitForCameraSettled`, « Timeout 5000ms exceeded while waiting on the predicate ». Les cinq `trace.zip` conservés montrent la position de la caméra lue par le helper : même trajectoire dans les cinq (z = 21,45 → 19,13 → 17,40 → 14-16 → 11,8 → 11,43 → 11,38 → 11,377 m, le repos étant à 11,375), expiration à 4,94-4,95 s avec un dernier écart de 6 à 9 mm pour 5 mm exigés. À l'expiration la caméra était donc à ~2 mm de son repos : elle avait convergé, c'est la lecture suivante (1 s plus tard) qui aurait validé le critère. Les autres tests de `movement.spec.ts` (glissé, clavier) n'étaient pas touchés.
Cause : la convergence se compte en **images**, pas en secondes. `Player.tsx` borne `dt` à 1/15 s (protection contre un onglet qui revient au premier plan) ; sous 15 images/s, chaque image rapproche donc la caméra de 1 − e^(−6/15) ≈ 33 % du chemin restant, quelle que soit la durée réelle de l'image. Il faut ~18 images pour passer de ~10 m (saut du spawn au point libre du hall, plus le recul de caméra du dialogue d'accueil qui se referme) à moins de 1 cm. Les runners CI (SwiftShader, 2 cœurs) rendent ~5 images/s (déduit de la vitesse de convergence dans les traces : facteur ≈ 0,15 par seconde pour 0,67 par image) : ~4 s de convergence, ~6 s pour que deux lectures espacées d'1 s passent sous 5 mm, contre un budget de 5 s. Sur un poste de développement (images bien plus rapides) le test passe, d'où l'impression d'un flake lié à la charge. Ce n'est pas un bug du jeu : une caméra « au ralenti » sur un appareil lent est l'effet voulu de ce plafond de `dt`.
Reproduit en local en retardant `requestAnimationFrame` de 185 ms (≈ 5 images/s, script jetable non conservé ; 8 exécutions, projet `android`, ancien helper) : 2 échecs identiques à ceux de la CI (expiration à 4,93-4,96 s, même trajectoire de caméra, dernier écart 9 mm) et 6 sorties anticipées après ~110 ms, caméra encore à 10 m de son repos — deux lectures tombées sur la même image passaient pour une caméra immobile, et le tap était alors visé depuis une caméra en transit (écran x ≈ 5 px au lieu de 206). Ces 6 passages ne prouvaient donc rien.
Corrigé côté test, dans `waitForCameraSettled` uniquement : échantillonnage image par image (`requestAnimationFrame`, dans la page) au lieu d'un `expect.poll` à intervalle de temps ; calme exigé sur 3 images consécutives (< 5 mm chacune) ; budget porté de 5 s à 20 s (~4 s attendues à 5 images/s, marge ×4 ; aucune attente ajoutée sur une machine rapide, on sort dès le calme constaté). Mêmes 8 exécutions avec le nouveau helper : 8 réussites, attente de 4,6 à 5,1 s (jusqu'à 12 s quand la machine de développement était saturée par ailleurs), cible toujours visée au même pixel (206,0 ; 535,9). Les assertions du test (marqueur de tap visible, joueur qui avance vers la cible, vers −Z) sont inchangées.

**Contamination de test évitée (pas un bug applicatif)** — `presence.spec.ts` › *un seul contexte*, observé en faisant échouer `peersCount` à une valeur non nulle lors des premiers essais : plusieurs specs qui entrent en jeu (`enterMuseum`) au même instant (n'importe lesquelles, `fullyParallel: true`) rejoignent réellement le même canal Supabase Realtime (`room-1`) — un vrai autre visiteur d'un AUTRE test au même moment, pas un fantôme de l'app. Corrigé côté test (`e2e/presence.spec.ts`) : ce test bloque désormais sa propre connexion Realtime (`page.routeWebSocket`, jamais de vrai réseau) pour rester déterministe quelle que soit la charge de la suite ; voir le commentaire en tête du fichier.

**Suite complète et charge parallèle sur cette machine** — la suite complète (`pnpm exec playwright test`, 3 projets, 4 workers par défaut sur cette machine à 8 cœurs) a occasionnellement fait dépasser un budget de chargement par défaut (15 s) à un test ouvrant plusieurs contextes supplémentaires (`presence.spec.ts` › `@live`) : disparu à `--workers=2`. Probablement de la contention CPU pure (plusieurs scènes SwiftShader simultanées sur un nombre de cœurs limité, comme pour le résidu du flake `movement.spec.ts` ci-dessus après son correctif — un mécanisme distinct de sa cause racine, déjà corrigée), pas un bug de présence — noté ici en toute transparence plutôt que masqué ; une CI avec plus de cœurs dédiés ou moins de contention ne devrait pas le reproduire.

## 3. Vérifications CI (`.github/workflows/ci.yml`)

Trois jobs, enchaînés sur chaque PR : `quality` (lint + typecheck + `pnpm test`), `build` (`pnpm build` + `verify:bundle`/`verify:security`/`verify:content`), `e2e` (installe Chromium via `playwright install --with-deps chromium` puis `pnpm e2e`). Le rapport HTML et les traces (`playwright-report/`, `test-results/`) sont archivés 7 jours en cas d'échec.

Le build que sert `pnpm e2e` en CI reçoit un faux projet Supabase (`VITE_SUPABASE_URL`/`VITE_SUPABASE_ANON_KEY` factices, posées par `playwright.config.ts` quand `CI` est défini) ; `gotoMusee` répond à sa place (`e2e/support/supabaseStub.ts`, détails dans `docs/tests/archives.md`). Sans cela le jeu ne lit jamais Supabase en CI (aucun secret, aucun `.env.local`) et les tests qui interceptent ses requêtes ne sont jamais sollicités. Le job `build`, lui, reste sans aucune variable : c'est le bundle de production sans configuration.

En local, la même commande (`pnpm e2e`) télécharge/utilise le Chromium géré par Playwright ; `PW_CHROMIUM_PATH` (voir plus haut) permet de pointer vers un Chrome for Testing déjà présent sur la machine si le téléchargement Playwright n'est pas disponible.

## 4. Limites connues

- SwiftShader (rendu logiciel) est nettement plus lent qu'un GPU de téléphone réel : le test de performance indicatif (images/s) n'est pas un budget. Le budget de dessin (`≤ 150 appels`, `performance.spec.ts`), lui, est une assertion stricte, désormais possible grâce à `window.__musee.renderInfo()` (voir plus haut) : mesuré au spawn et au milieu de chaque aile, largement sous la limite en pratique (spawn ≈ 50, ailes ≈ 65–80 appels sur cette machine).
- Sous forte charge parallèle (plusieurs workers, plusieurs scènes SwiftShader simultanées), cette machine (8 cœurs) peut faire flaker un test ponctuellement par pure contention CPU/thread principal, sans rapport avec le code testé — voir « Découvertes » ci-dessus (`presence.spec.ts` › `@live`). `--workers=2` (au lieu du défaut) réduit fortement le risque en local sur ce type de machine.
- `movement.spec.ts` › *tap au sol* (voir les deux correctifs ci-dessus) : le test attend la convergence de la caméra, qui se compte en images rendues (plafond de `dt` à 1/15 s dans `Player.tsx`), pas en secondes. Sous une contention extrême (`--repeat-each=20 --workers=4`, une quarantaine de processus Chrome SwiftShader sur 8 cœurs), 2 échecs sur 40 avaient subsisté après le premier correctif : l'hypothèse d'une perte de contexte WebGL avait été avancée, mais jamais observée ; le budget d'attente trop court du helper (cause de la CI du 30/09) les explique sans elle. Le budget est désormais de 20 s pour ~4 s attendues à 5 images/s. Sur une machine encore 2 à 3 fois plus lente que la CI actuelle, c'est le délai de 60 s du test lui-même qui deviendrait le facteur limitant : son `beforeEach` dure déjà ~18 s sur la CI, dont ~12 s pour refermer le dialogue d'accueil clic par clic.
- Les tests de présence temps réel (`presence.spec.ts`) dépendent d'un vrai projet Supabase Realtime (`.env.local`) pour le test `@live` ; sans réseau ou sans `.env.local`, il est ignoré proprement (`test.skip` conditionnel, voir `e2e/support/supabaseEnv.ts`). Le test « seul » ne dépend lui d'aucun réseau réel (websocket mocké ; en CI, le faux projet ferme de toute façon tout websocket Realtime).
- Les fiches exposées sont actuellement les 100 fiches d'attente fictives (`src/data/placeholder.ts`) : les tests qui piochent des identifiants de personnes (`state().people`) ne dépendent d'aucun nom réel et resteront valables une fois la vraie liste importée (le contrat `Person`/`ExhibitWingId` ne change pas).
